Team 6 – M3 Report: Multi-Agent Meeting Action-Item System

Repository: SamTusick/TeamProject6_AI_Agent  |  Extractor agent + Resolver agent (ReAct) + persistent memory, with code-level guardrails and human approval
Honesty statement. Cost figures, prices and conversion rates below are assumptions we have not yet validated with vendors or users; each is labeled and can be swapped in the formulas. The system is a working prototype, not a polished product. Known failures are listed in §7.

1. What the system does

Small teams lose decisions after meetings because nobody reliably separates a real commitment from a hedge or an idea. Our system reads a meeting transcript (imported, typed, or produced on-device from a recording with the open-source Whisper model in our desktop app) and produces human-approved action items, each tied to a verbatim quote. Approved items are written through the official MCP Filesystem server and also stored in a memory layer for later meetings.

2. Updated architecture

Roles, handoff and reasoning

ComponentDetail
Extractor agentbackend/agents/extractor.py. Single LLM call (NRP-hosted model; qwen3 / glm-5). Classifies candidates as CONFIRMED, TENTATIVE, DISCUSSED_ONLY, NEEDS_INFO; the prompt biases toward the lower-confidence label.
Resolver agentbackend/agents/resolver.py. Separate system prompt and loop. Only job: find a missing owner/deadline stated elsewhere in the transcript, or report that it is not stated.
Handoff triggerbackend/agents/handoff.py. The Extractor emits NEEDS_INFO (decisive language but missing owner and/or deadline).
Handoff payloadItem (title, quote), list of missing fields, full transcript, memory handle. The return value is the same item, upgraded to CONFIRMED only when both fields have verified quotes.
Reasoning patternReAct, implemented explicitly: JSON {thought, action, input} per turn; observations fed back; hard cap of 5 steps; unusable replies stop the loop.
Knowledge / memorybackend/core/memory.py. Persistent JSON store of human-approved items with lexical TF-IDF retrieval (RAG-lite, no embeddings). Used for search_memory hints and cross-meeting duplicate detection.
Guardrails(1) quote verification and value-in-quote check in code (backend/core/guardrails.py), (2) eligibility rule, (3) human confirmation, (4) memory is never evidence, (5) MCP server sandboxed to ./output, (6) consent prompts before recording or transcribing.

4. Operational cost model (100 / 1,000 / 10,000 users)

Assumptions (all replaceable)

  • Usage: 8 meetings per user per month, 30 minutes each; transcript ≈ 7,000 input tokens.
  • LLM price (assumed commercial mid-tier model, since the NRP endpoint is a free research platform and not a production service): $0.50 / M input tokens, $2.00 / M output tokens.
  • Extractor: 7,000 in + 800 out ≈ $0.0051/meeting. The Resolver fires on ~30% of meetings (assumption): 3 steps × 7,200 in + 150 out ≈ $0.0117 → $0.0035 expected. LLM ≈ $0.0086/meeting.
  • Speech-to-text (base case): $0 to us. The desktop app runs open-source Whisper on the user's own computer, so there is no per-minute API cost. The trade-off is the user's hardware and a one-time ~150 MB model download.
  • Speech-to-text (alternative: hosted Whisper API for a web or mobile version): assumed $0.006 per audio minute for 50% of meetings.
  • Hosting/infra ($40 / $250 / $2,200) and other per-user costs (storage, email, logging: $0.10/user) are rough estimates.
  • Price assumption for margin only: $12 per user per month.

What this tells us. Running speech-to-text on the user's device removes the largest variable cost; the LLM is then under 20% of cost at every scale and fixed hosting dominates. If the Resolver fires on 100% of meetings instead of 30%, LLM cost rises about 2.4× (≈ $0.02/meeting) – still small. Sensitivity: if only 25% of 100 users pay, revenue is $300 against $57 cost – positive, but payroll is not covered; at this scale the product is not self-sustaining without outside funding. Risks not modeled: model price changes, retries after failures, abuse, a free tier, and support cost for users whose computers are too slow for local Whisper.

Sustainability risks and mitigations. (1) Vendor dependence on LLM pricing – keep the model name in .env so models are swappable. (2) Privacy – recordings of people on calls: consent prompts, local storage and local transcription by default, no audio leaves the device, documented retention. (3) Accuracy trust – one false "decision" damages credibility, so we favor precision and always show the source quote. (4) Environmental footprint – small models, short prompts, a capped 5-step Resolver, and a small on-device Whisper model keep inference light. (5) Team sustainability – clear ownership by folder (backend, frontend, business docs) and automated tests keep handoffs between teammates safe.

6. User testing plan

  • Participants: 8–10 people from 3–4 small teams (student project groups and one small business), each running at least 2 real meetings. Consent for recording is obtained from every attendee; participants can delete data at any time.
  • Protocol: Week 1 – 30-minute onboarding; participants record or import a meeting. Week 2 – they review the extracted items, approve/reject, and record whether each item was correct. We observe one session per team (think-aloud) without coaching.
  • Measures: precision and recall against participants' own list of real commitments (collected independently before they see the output); time from meeting end to approved list vs. their usual method; number of rejected/edited items; SUS usability score (target ≥ 68); trust question "Would you act on this item without checking the quote?"; willingness to pay (ask for a price, not a yes/no); Whisper word-error observations on their real audio.
  • Success criteria: ≥ 90% of approved items judged correct; ≥ 60% of true commitments found; ≥ 6 of 10 participants say they would use it again; no unconsented recording incidents.
  • Ethics / data handling: store transcripts locally; anonymize names in anything shared in the report; delete the data after analysis.
  • What we will do with failures: every false item or missed commitment is logged with the transcript snippet and added as a regression test.

7. Limitations and failures we have observed (honest section)

  • Model endpoint outage. During testing the default qwen3 endpoint hung for 5+ minutes on even a trivial prompt, while glm-5 answered in ~3 s. We switched models via MODEL_NAME; the agent has no timeout/fallback yet – an open bug.
  • The handoff is rare on easy transcripts. On f_resolvable the Extractor resolved owner and deadline itself, so no handoff occurred. We verified the Resolver by running it directly on that transcript (it found both with quotes) and on d_needs_info (it correctly gave up). Different models also reason differently: glm-5 searched the transcript before answering, while qwen3 answered after one thought.
  • Resolver quotes can span a speaker label (e.g. "Morgan: Thanks. Back to the pricing page …"); the check accepts this because it is verbatim text.
  • Memory is lexical, and the desktop app does not write to it. A paraphrased duplicate is missed; only items approved through the terminal CLI are remembered (the desktop app reads memory but does not save approvals to it); no concurrency control.
  • Speech-to-text is moderately accurate. Whisper base transcribed a LibriSpeech test clip with a few word errors ("were sleeping" became "are sleeping"; "a cooing dove" became "accuing dove"). Real multi-speaker calls have not been tested. The first run needs internet to download the model. We first built a Wispr Flow cloud integration but removed it because Wispr's API is closed to new users, so it could never be tested against the live service.
  • Non-determinism. The same transcript can give different labels on different runs.
  • Scale. Single-user JSON memory; no auth or multi-user backend yet, so the 1,000 and 10,000-user rows are cost estimates, not tested capacity.
